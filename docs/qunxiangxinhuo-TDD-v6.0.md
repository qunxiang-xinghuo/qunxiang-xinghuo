## 一、v6.0 核心设计理念

### 产品诊断（v5.x遗留问题）
1. **泡泡路径过长**：点击→详情→选模式→选身份→等待，5步流失率60%+
2. **等待无感知**：15秒纯等待，用户焦虑
3. **对白室过于复杂**：状态栏/保存/结束/围观人数/火花墙，干扰对话
4. **AI催化静态**：4个固定提示，不会根据对话动态变化
5. **脑洞门槛过高**：医疗/法律等专业场景，普通人难以代入
6. **素材库概念模糊**：用户不知道"素材"是什么
7. **底部导航宽度过长**：在移动端超出屏幕宽度

### v6.0 新设计原则
- **降低门槛**：日常场景，50字以内，秒懂
- **极简对白**：只保留标题+对话流+AI催化+输入框
- **动态AI**：DeepSeek+知乎直答双API，30秒刷新，基于上下文生成问题
- **刘看山兜底**：15秒未匹配→直接切换AI对话，不放弃任何用户
- **火花代替素材**："火花"是灵感碰撞的瞬间，比"素材"更有情感
- **底部导航适配**：max-width: 480px 居中，适配所有手机屏幕

## 五、双人匹配修复（v6.0-fix2）

### 5.1 流程图

```
/duo-match（身份选择）
  → /duo-waiting（15秒倒计时）
    → 匹配成功 → /room/[id]（双人WebSocket对白）
    → 15秒超时 → 显示"与刘看山对话"按钮
      → 点击 → POST /api/rooms/ai → /room/[id]（AI对白）
      → 再次尝试 → 重新发起匹配请求
```

### 5.2 等待页简化

**移除：**
- 四级策略可视化（4个指示灯+进度条）
- "刘看山已派出X个信号波"文案
- 复杂的策略标签

**保留：**
- 刘看山头像
- "正在匹配中..."文字
- 倒计时数字+进度条
- 匹配成功/超时的简单提示

### 5.3 并发匹配Bug修复

**问题：** 两个用户几乎同时选择匹配时未匹配上

**根因：** 用户A创建waiting请求和用户B查找waiting请求之间的时间窗口，导致并发竞态条件

**修复方案（v6.0-fix2）：**
1. 阶段1：同brainhole精确匹配（直接命中其他waiting用户）
2. 阶段2：任意waiting用户匹配
3. 阶段3：创建自己的waiting请求
4. **阶段3b（新增）：创建请求后，立即执行"二次匹配"查找**
   - 查找除自己外最新的waiting请求
   - 如果找到，立即匹配（而不是进入waiting状态）

**代码实现：**
```typescript
// 创建自己的matchRequest后
const retryMatches = await db.matchRequest.findMany({
  where: {
    status: "waiting",
    userId: { not: userId },
    id: { not: matchRequest.id }, // 排除自己刚创建的
  },
  orderBy: { createdAt: "asc" },
  take: 1,
});

if (retryMatches.length > 0) {
  // 立即匹配，不进入waiting状态
  return await createDuetMatch(...);
}
```

## 十二、火花墙系统（/library）

### 12.1 公共火花墙
- **入口**：底部导航「火花」Tab → 公开火花
- **排序**：按 `hotScore` 降序（而非时间倒序）
- **数据源**：`GET /api/sparks/public?limit=50`
- **字段**：内容预览、脑洞标题、作者身份、日期、热度值

### 12.2 我的火花
- **入口**：底部导航「火花」Tab → 我的火花 / 我的页 → 我的火花
- **显示**：个人所有对白资产（Asset），含公开/私密状态
- **公开/私密切换**：每条火花右侧开关按钮
  - `PUT /api/sparks/:id/visibility` — 只能修改自己的Asset
  - 设为公开后同步进入公共火花墙

### 12.3 对白结束自动保存
- 对白室底部「结束对白」按钮
- `POST /api/assets` — 从room创建Asset
- **默认私密**：`isPublic: false`
- **热度计算**：`hotScore = sparkCount * 10 + messageCount`
